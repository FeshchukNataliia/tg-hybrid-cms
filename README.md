## Огляд архітектури
Цей проєкт — високопродуктивний бекенд-шлюз для агрегації, маршрутизації та автоматизованого планування контенту. 

Система побудована з використанням **подійно-орієнтованої архітектури (Event-driven)**. Це дозволяє відокремити прийом клієнтських API-запитів від важких процесів обробки медіа та відправки даних. Замість блокування основного потоку під час відкладеної публікації, система використовує асинхронні черги (Queues) та фонових воркерів (Workers) для гарантованої доставки контенту без втрат продуктивності.

## Технічний стек
- **Платформа:** Node.js (Non-blocking I/O)
- **Мережевий шар:** Express.js (REST API, Middleware pipeline)
- **База даних:** PostgreSQL (зберігання реляційних сутностей та логів транзакцій)
- **Обробка даних:** Node.js Streams (для оптимізації пам'яті при роботі з медіафайлами)

## Ключові сутності та Пайплайн

1. **Post (Payload)**
   - Ядро системи. Містить уніфіковану структуру контенту: текстові блоки, масиви медіафайлів (для генерації візуальних каруселей), метадані для інтерактивних елементів (кнопки, квізи). 
2. **Schedule (Тригери та Черги)**
   - Менеджер відкладених завдань. Призначає публікаціям часові мітки (timestamps) і контролює їхній перехід у чергу на виконання, коли настає час тригеру.
3. **Worker (Фоновий обробник)**
   - Ізольований процес, який "слухає" чергу. Забирає готовий `Post` і виконує мережеві запити до зовнішніх API, не навантажуючи основний сервер шлюзу.
4. **Channel (Точки інтеграції)**
   - Сутності з налаштуваннями доступу (наприклад, API-токенами для Telegram-ботів) та правилами маршрутизації контенту.
5. **User (Керування)**
   - Авторизація, адміністрування підключених каналів та моніторинг статусів виконання (pending, published, failed).

## Потік виконання (Data Flow)
`Запит (HTTP/JSON)` → `Валідація (Middleware)` → `Збереження в БД (PostgreSQL)` → `Очікування тригеру (Schedule)` → `Обробка воркером (Queue)` → `Публікація (External API)`
