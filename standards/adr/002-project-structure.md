# Архітектура подієво-орієнтованої CMS

- **Статус:** Прийнято
- **Дата:** 2026-10-23

## Контекст і Проблема
Синхронна публікація контенту в Telegram через API може призводити до блокування головного потоку Node.js та таймаутів для клієнта (особливо при Rate Limits 429).

## Розглянуті альтернативи
1. Монолітний підхід (обробка в контролері Express).
2. Розподілена архітектура (API Gateway + Queue + Worker).

## Прийняте Рішення
Обрано **Розподілену архітектуру**. API Gateway лише приймає запити, а Worker обробляє їх фоном.

## Наслідки
### Плюси
- API Gateway не блокується важкими задачами.
- Воркери можна масштабувати незалежно.
### Мінуси
- Зростає складність інфраструктури (потреба в диспетчері черг).
