# Специфікація: Telegram Hybrid CMS (v1.0.0)

## 1. Що і Навіщо (Мета)
Гібридна CMS для створення та керування контентом Telegram-каналів. Мета етапу — реалізація багаторівневої архітектури (Роути -> Сервіси -> Репозиторії), інтеграція з реляційною БД та впровадження наскрізного логування бізнес-процесів (Trace ID).

## 2. Архітектура та Межі (Модулі)
- Обрано AsyncLocalStorage для керування залежностями та контекстом запиту
- Обрано PostgreSQL з драйвером postgres для роботи з БД
- Routes → Services → Repositories
- EventBus → фоновий Worker
- Додано ізоляцію конфігу через .env
- Додано відкладений пул БД

## 3. Критерії прийняття 2 лаби
- Усі сценарії працюють через HTTP API.
- Шари декомпозовані: SQL тільки в DAO/Репозиторіях, бізнес-логіка в Сервісах.
- Trace ID (business-process ID) прокидається на всі рівні без передачі через параметри функцій (через AsyncLocalStorage / DI).
- БД ініціалізується на старті з перевіркою `SELECT now()`. 
- Наявність ендпойнта GET /version.
- Автоматизація smoke-тесту

## 4. Сценарії помилок
- **400 Bad Request:** Помилка валідації вхідних даних (наприклад, порожній title), некоректний ID тепер повертає 400, а не 500.
- **404 Not Found:** Спроба опублікувати неіснуючий пост.

## 5. Схема БД (Логічна)
- `users`: `id` (PK), `username`, `created_at`.
- `posts`: `id` (PK), `user_id` (FK), `title`, `content`, `status` (draft | queued | published | failed), `created_at`.
- Сутності Channels, QueueJobs та поле content_payload із моделі Завдання 1 свідомо відкладено на наступні етапи

## 6. Основні сценарії та очікувана поведінка (API)
- **POST /posts:** Створення чернетки поста. Очікується валідація тіла запиту (title, content). Повертає 201 Created та дані поста.
- **GET /posts** повертає стрічку постів разом із даними автора одним оптимізованим запитом (LEFT JOIN) без N+1
- **POST /posts/:id/publish:** Ідемпотентний атомарний перехід: draft → queued → published / failed, 200 OK.
- **GET /version** повертає поточну версію API та статус ok, 200 OK
