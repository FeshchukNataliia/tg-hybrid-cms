# Аудит використання AI (Лабораторна 1)

## Ітерація 1: Інженерні стандарти та DoD
**Промпт:** "Який формат ADR та Definition of Done обрати для проєкту?"
**Відповідь AI:** Запропоновано Класичний MADR + Enterprise DoD (суворий контроль) або Lightweight ADR + Базовий DoD.
**Рішення студента:** Обрано Класичний MADR та Строгий DoD, щоб одразу закласти правильні процеси перевірки коду через Husky та Biome.

## Ітерація 2: Проєктування специфікації (spec.md)
**Промпт:** "Згенеруй spec.md за підходом Bottom-Up (від бази даних)."
**Відповідь AI:** Згенеровано базовий каркас (Users, Channels, Posts, QueueJobs) із 3 архітектурними спрощеннями: відсутність RBAC, зберігання медіа як URL, відсутність Exponential Backoff.
**Рішення студента:** Спрощення були свідомо прийняті для версії V1 як технічний борг і задокументовані в DEFENSE.md.

## Ітерація 3: Реакція на Code Review (Аудит меж модулів)
**Промпт:** "Як провести реальний аудит меж модулів, який вимагає викладач?"
**Відповідь AI:** Запропоновано імітацію (додавання зайвих NPM пакетів) або реальне порушення архітектури в коді (створення прямого імпорту Worker в API).
**Рішення студента:** Я обрала другий шлях. Створено коміт із технічним боргом (прямий виклик), проведено аудит, API повністю ізольовано від Worker, що підтверджує розуміння Event-Driven архітектури (виправлено в окремому коміті).

## Ітерація 4: Налаштування Smoke-тестів
**Промпт:** "Як реалізувати справжній smoke-тест?"
**Відповідь AI:** Запропоновано синтетичний тест (проста математика) або повноцінний інтеграційний тест API Gateway (через `supertest`).
**Рішення студента:** Я обрала інтеграційний тест. Це зайняло більше часу, але дозволило перевірити реальну відповідь `/health` роуту. Для автоматизації хуків підключено `lint-staged`.
